# v0.2 本地运维与升级

v0.2 修复审查发现的 SSH 日志注入、日志来源校验、认证重复计数、正常回包
扫描误报、Telegram 限流/成功确认、重复日报查询、月界计费、Unicode 队列
配额、IPv6 非首片和扫描状态淘汰问题。公开验证范围与未完成事项见[当前限制](ALPHA_LIMITATIONS.md)。
历史 v0.1 VM 验证不能替代本版本验证。

## 升级顺序与兼容性

- 配置仍为 schema 1；缺省增加 `storage.max_bytes=1073741824` 和
  `storage.min_free_bytes=134217728`。原配置可以继续加载。
- 数据库迁移到 schema 3，保留 v1/v2 的事件和聚合。新增日志游标、覆盖历史、
  日报快照、队列过期/隔离/限流与计数。旧版本不能读取 schema 3；回退须使用
  升级前的一致性备份，不能只替换旧二进制。
- sensor 写 protocol 3，增加远端端口；daemon 接受 protocol 1/2/3。
  先升级 daemon，再升级 sensor，或同时停止并替换两个程序。旧 sensor 的 UDP
  扫描覆盖标为不完整，因为旧协议没有请求/应答匹配所需的远端端口。
- daemon 只接受 `noderampart-sensor` UID；CLI/sensor 校验 `noderampart` daemon
  UID。服务账号缺失会报错。`--manual-current-uid` 仅用于明确选择同 UID 的
  手工实验，不进入生产 unit。
- 源码安装和原生包混用会被拒绝。源码切换到包安装前使用
  `sudo ./scripts/source-to-package.sh --prepare`；该操作只删除所有权清单验证
  通过的源码程序/完整 unit，保留配置、数据库和管理员 drop-in。v0.1 遗留源码
  安装需要精确的旧构建产物，见脚本的 `--legacy-checkout` 模式。
- Debian 升级保留管理员的启用/禁用状态，只重启仍在运行的服务，并遵守服务
  启动策略。RPM 首次安装仍遵循发行版 preset；升级可更新未修改的旧默认
  配置。管理员修改的配置按 `%config(noreplace)` 保留，新默认文件可能另存。

默认存储预算使用 SQLite DELETE 回滚日志、FULL 同步和独占连接。1 GiB 的
活动文件预算对应约 511 MiB 的数据库页上限，其余保留给回滚日志；不再依赖
WAL 文件的定期采样来声称硬配额。既有数据库过大时启动会明确失败，需增加
预算或从压缩快照恢复。预算、低磁盘水位、内存和外部备份文件的边界见
[存储预算说明](STORAGE-BUDGET.md)。运行时不允许另一个 SQLite 连接绕过预算；
使用 CLI 查询，或停服务后进行离线维护。

## 健康与通知

```bash
sudo noderampart doctor
sudo noderampart status
sudo noderampart notify status
sudo noderampart notify list --limit 20
sudo noderampart notify test
```

`notify test` 返回 `queued` 和消息 ID，仅证明入队；送达需查看队列中的 `sent`
以及 `last_sent_utc`。诊断包含采集/持久化新鲜度、未恢复的存储操作失败、活动
数据库文件大小、队列字节/最早积压/拒绝数、隔离数量和目标限流期限。
`doctor` 在配置缺失或损坏时仍输出脱敏检查结果，但无法猜测自定义路径。

```bash
sudo noderampart notify retry --id msg_EXAMPLE
sudo noderampart notify quarantine --id msg_EXAMPLE
sudo noderampart notify resume --destination telegram
```

实际 ID 从 `notify list` 获取。隔离会阻止尚未开始的后续发送，但不能撤回已经在途的请求。单条重试不会绕过目标限流；`resume` 是显式解除
目标限流并使尚未隔离的有效消息可再次发送。永久失败立即隔离；连续 10 次
失败后停止自动重试。未发送消息（含隔离消息）7 天过期，已发送记录保留
30 天。待发与隔离正文合计受 10,000 条/32 MiB UTF-8 字节限制。
超过 30 天或无法表示的服务端等待进入需人工解除的目标暂停，不自动缩短等待。
Telegram 的响应正文、token、chat ID 不进入诊断错误。

网络检测事件在落库前进入有界内存重试队列：最多 1,024 条、4 MiB 序列化
正文；状态的 `event_ingest` 包含待写条数/字节、最早观察时间、最近成功时间
和丢弃计数。重试保留原事件 ID 与通知去重键，每秒及新批次处理时尝试恢复，
单次最多 64 条、两秒。正常关闭在统一两秒内尽量排空。
容量或元数据边界导致的丢弃会累计并在存储可写后记录覆盖缺口。
该队列不是跨进程持久日志：重启记录 `process_restart_pending_unknown`，
计数 0 表示无法确定旧进程待写损失数量，不表示确认没有丢失。关闭仍有待写
时会尝试记录确切数量；若存储依旧不可用，只能保留日志计数和下次启动的不确定标记。

## 日志恢复和覆盖

journal reader 自动重启，采用 1 秒到 1 分钟退避。默认最多补读 15 分钟、
10,000 条记录。每条记录的统计、事件、通知和游标在同一事务提交后才确认；
有界游标缓存防止正常重放重复计数。日志来源必须匹配可信 root UID、SSH
可执行路径和 SSH systemd unit；发送者提供的 syslog 标签本身不可信。
`starting` 表示正在启动日志子进程；子进程启动成功即显示
`running / process_started`，不要求先收到新 SSH 记录。发生格式或来源异常后，
后续可信记录成功持久化会恢复为 `running / record_persisted`。
进程状态、最近持久化时间和历史覆盖缺口须一起检查；`running` 本身不证明
已经提交新记录或历史覆盖完整。

有效游标保留同一微秒内的顺序。游标被轮转清除时，从最后确认时间之后有界
恢复，并记录覆盖缺口；无法证明顺序的同微秒边界不作“完整恢复”承诺。
读取失败、来源异常和补读截断会出现在诊断/覆盖记录中。组件覆盖保留最多
10,000 段，显式缺口保留最近 1,000 项；未记录时间一律视为未知。

检测器的内存窗口在 daemon 重启后重建，状态给出完整窗口最早可用时间。
洪泛恢复要求连续、无已知丢失的观察窗口；低采样量不再直接等同于恢复。
TCP 扫描目前使用发起连接的 SYN；ACK/FIN 扫描不是同一条检测规则。UDP
请求匹配保留 30 秒、最多 16,384 个元组；冷启动、丢失和满表会降低扫描覆盖。

IPC 在 listener 生命周期内控制解帧节奏，最多每个配置批次间隔的二分之一
读取一帧（最小 50 ms），重连不会重置额度。合法积压可以逐步追赶；时间单调、
声明间隔、帧大小和对端身份检查仍保留。过期批次会入库，但实时采集状态保持
降级，直到收到新鲜批次。Socket 写成功仍不是 daemon 持久化确认。

## 历史与导出

```bash
sudo noderampart events list --since 2026-09-10T00:00:00Z --until 2026-09-11T00:00:00Z --limit 20
sudo noderampart events show --id evt_EXAMPLE
sudo noderampart report now
sudo noderampart report list --limit 20
sudo noderampart report show --date 2026-09-10 --format text
sudo noderampart report show --date 2026-09-10 --format html > report.html
```

列表返回继续分页的键，单次最多 100 条。事件展示和导出使用已按存储隐私
配置转换的数据；HTML 是转义后的独立静态页面，不包含脚本或远程资源。
日报即使 Telegram 关闭也会归档，按报告时区生成前一天的快照；快照保留
13 个月，不受 7 天事件明细清理影响。首次升级前已发出的旧日报没有原始
渲染快照，不会伪装成当时的归档。当前调度只生成前一天，不自动补齐长时间
离线的每一天；历史小时数据仍可用于后续分析。

日报采用本地日历日的真实起止时刻：缺失午夜从当天首个有效时刻开始，重复
午夜取首次。整日因时区变更被跳过时，报告最近实际存在的完整日期，不归档
零长度日期。调度时间落入缺失区间则顺延到首个有效时刻，重复时间取首次，
归档/投递仍按日期去重。认证来源因存储压力被合并时，排行显示
`Other source ranges (storage pressure)`；小时认证总量保留，来源明细已减少。

## 一致性备份与恢复

```bash
sudo noderampart backup create --output /var/lib/noderampart/backups/before-upgrade.db
sudo noderampart backup verify --input /var/lib/noderampart/backups/before-upgrade.db
sudo systemctl stop noderampart-sensor noderampartd
sudo noderampart backup restore --input /var/lib/noderampart/backups/before-upgrade.db --output /var/lib/noderampart/restored.db
```

在线备份使用 `VACUUM INTO`，验证完整性和受支持 schema 后发布一个新的
0600 文件。路径中的符号链接、已有输出和活动 SQLite sidecar 会被拒绝。
在线备份限时两分钟，输出仅允许位于状态目录的 `backups` 直接子目录；
备份占用单独的磁盘空间，不计入活动数据库预算。

恢复只创建新数据库，不覆盖原数据库。验证后由管理员把配置中的
`paths.database` 指向新文件，确认其所有者为 `noderampart:noderampart`，
执行 `config test` 后启动服务。保留原配置与数据库直至恢复验收完成。
不要直接复制运行中数据库的单个 `.db` 文件，也不要在未停止 daemon 时
替换数据库。备份包含与原数据库同等敏感的数据，应自行安全保管。
